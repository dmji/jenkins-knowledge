# Catalog validator

Validate a catalog against the repository schema and semantic reference rules.

\`\`\`sh
cargo test --manifest-path crates/catalog-validator/Cargo.toml
cargo run --manifest-path crates/catalog-validator/Cargo.toml -- \\
  examples/catalog/catalog.json schemas/catalog.schema.json
\`\`\`

Exit codes: \`0\` valid, \`1\` catalog validation failed, \`2\` input/usage error.

## Catalog validation semantics

Catalog validation is shared by the Builder and Runtime. Structural JSON Schema validation runs first; semantic validation then checks relationships that JSON Schema cannot express.

### Field evidence

Every fieldEvidence key must name a property declared by the schema's symbol definition and that property must be present on the symbol. The evidence and fieldEvidence metadata containers cannot themselves be assigned field evidence. This is intentionally strict: a typo or stale attribute cannot silently claim a confidence level.

### Evidence/source compatibility

| Evidence kind | Compatible source kinds |
|---|---|
| controller-observed | jenkins-controller, plugin, jenkins-core |
| source-scanned | shared-library, plugin, jenkins-core |
| static-model | jenkins-controller, jenkins-core |
| inferred | any defined source kind |

Every evidence sourceId must resolve to a source. Unknown evidence kinds remain rejected by the schema rather than being silently interpreted.

### Manifest reconciliation

For every catalog source, manifest.sourceRevisions and manifest.provenance must each contain exactly one matching entry. Revisions, names, kinds, and optional URLs must agree with the catalog source. Missing and extra source keys are errors. The known provenance fields are required; additional fields inside a provenance record are allowed and preserved for forward compatibility.

Older hand-authored package manifests with empty sourceRevisions/provenance maps must be regenerated by the Builder. They are no longer considered consistent with a non-empty catalog. This does not change the catalog schema version; it tightens the package-level consistency contract.

### Coverage semantics and forward compatibility

Known surfaces are checked against their compatible source kinds. For known symbol surfaces (Pipeline steps, Declarative directives, Shared Library vars/src, methods, classes, and properties), a status other than inspected is rejected if matching symbols or evidence from that source are present. An inspected surface may legitimately contain zero symbols.

Unknown coverage surface names are allowed for forward compatibility; source references and duplicate source/surface pairs are still validated, but no surface-specific inference is made until the surface is known. Unknown additional fields inside provenance records are also allowed. Unknown top-level catalog or manifest fields remain rejected by their JSON Schemas.


## Secret-bearing metadata

Secret key names are normalized by removing punctuation/separators and folding case before matching. The policy covers passwords/passphrases, API/access/private keys, tokens, secrets, credentials and credential IDs, authorization/bearer/basic-auth headers, cookies, and session identifiers. It is applied recursively through objects and arrays, including source metadata, controller snapshots, symbol metadata, coverage records, and manifest provenance.

This is heuristic defense in depth, not a guarantee that arbitrary secret values can be recognized. Values stored under innocuous field names may not be detectable; collectors should expose only explicitly safe metadata and must not copy authentication material into catalogs, diagnostics, or fixtures.

The shared redactor removes matching fields, removes URL user information, and strips query strings/fragments from URL-like fields (URL, URI, documentation URL, base URL, and endpoint) while preserving non-sensitive sibling metadata. The Jenkins GDSL Collector, Shared Library Scanner, and Builder use this same redactor before validating or publishing their outputs. Direct catalog/manifest validation rejects any remaining secret-bearing key or URL query parameter. Error messages report paths and key names only; they never include secret values.

Ordinary API signatures (for example, a Pipeline method signature) are not treated as secrets. Signed URL query parameters such as sig/signature are rejected and removed with the rest of the URL query.
